# Baby Name Swipe

A two-person baby-naming app: each parent swipes through a shared name deck independently, and a "match" happens when both keep the same name. Single-page, mobile-first. As of spec 002, sign-in is required and a FastAPI backend is the system of record — the browser's localStorage is now an offline cache and sync outbox, not the source of truth.

## Stack & hosting

- **Frontend**: Vite + React + TypeScript, styled entirely with inline `style={}` objects (no CSS framework in practice, despite Tailwind being wired up).
- Almost the entire UI lives in one file: `src/BabyNameSwipe.tsx`. It carries `// @ts-nocheck` deliberately — it was ported as-is from a JS prototype and isn't worth retyping. Don't "fix" this by adding types unless asked.
- `src/App.tsx` is a one-line wrapper; `src/lib/` holds: `storage.ts` (localStorage get/set shim), `auth.ts` (Supabase magic-link sign-in/out, session), `api.ts` (typed fetch client for the backend's `/v1` endpoints), `syncQueue.ts` (offline outbox: append, flush, retry), `useUpdateCheck.ts` (update-banner polling hook), `global.d.ts` / `vite-env.d.ts` (ambient types). `nameCorpus.ts` is gone — the corpus is server-side now (see Name pools below).
- **Backend**: `api/` — FastAPI + SQLAlchemy 2.0 + Alembic on Python 3.12, Postgres (Supabase). `make check` (repo root) is the single gate: ruff + `pyright --strict` + pytest against a throwaway `testcontainers` Postgres, bootstrapping `api/.venv` on first run if it doesn't exist. See `api/README.md` for the test-first loop and `api/DEPLOY.md` for the manual deploy runbook (no CI/CD for the backend yet — deliberately the next spec).
- **Auth**: Supabase Auth (magic link only, no passwords). The backend verifies Supabase-issued JWTs offline against the project's JWKS endpoint — `algorithms` must come from the JWK's own `alg` field (`api/src/babynames_api/auth.py`), not be hardcoded, since Supabase projects created after its 2025 key rotation sign with ES256 rather than RS256. The built-in Supabase auth email sender only delivers to the project's team members and caps at 2/hour — see `docs/remaining-items.md` §1.
- **Frontend hosting**: Azure Static Web Apps (Free tier), resource group `baby-names-rg`, East US 2, on two separate SWA resources: `baby-names` (prod) and `baby-names-test` (staging). Prod is `https://baby-names.calebdudley.dev`, staging is `https://baby-names.test.calebdudley.dev`. Custom-domain DNS/TLS for both is managed centrally in the sibling `caleb-dudley-dev` repo via Terraform — see that repo's `docs/baby-names-domain-handoff.md` for the (fairly involved) history if either domain ever needs touching again.
- **Backend hosting**: Azure Container Apps, Consumption-only environment `baby-names-env` (same `baby-names-rg`), app `baby-names-api`. `minReplicas: 0` — this and the Consumption workload profile are both load-bearing for the $0 cost target; don't change either without reading `specs/002-backend-accounts-sync/research.md` §1 first. A daily scheduled Container Apps Job (`baby-names-keepalive`) pings the database directly (not through `/health`) to stop the free Supabase project from pausing after 7 days of inactivity — research §2. **Redeploying the API requires resolving the image digest explicitly and forcing a new revision** (`api/DEPLOY.md`'s "Build and push the image" section) — a Container App revision pins to whatever digest `:latest` resolved to at revision-creation time, so pushing a new image under the same tag and re-running `containerapp update` is a silent no-op that keeps serving the old code.
- Frontend deploys via `.github/workflows/azure-static-web-apps.yml` (prod, pushes to `main`) and `azure-static-web-apps-staging.yml` (staging, pushes to any other branch) — both **hand-written** (checkout → npm ci → write `public/version.json` with `github.sha` → `npm run build` with `VITE_COMMIT_SHA`/`VITE_API_BASE_URL`/`VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` env → deploy with `skip_app_build: true`), not Azure's auto-generated ones. The three `VITE_` backend-config vars come from GitHub repository secrets, set once via `gh secret set` (never committed) — without them a deployed bundle silently falls back to an empty Supabase config and `http://localhost:8000`, so sign-in fails at runtime with a perfectly green build.
- Every push to `main` auto-deploys the frontend to prod; every push to any other branch auto-deploys to staging (`https://baby-names.test.calebdudley.dev`). Docs-only changes (`**.md`, `.specify/`, `specs/`, `docs/`) don't trigger deploys. Don't proactively monitor deploy runs — only investigate if a deploy is suspected to have failed or the user asks. The backend has no auto-deploy at all; a code change there does nothing to the live service until `api/DEPLOY.md`'s redeploy steps are run by hand.

## Data model & storage

- **The backend is the system of record.** `api/` owns accounts, swiper labels/positions, picks, the dealt-name order (`served_order`), and the corpus itself. See `specs/002-backend-accounts-sync/data-model.md` for the six-table schema.
- **The browser's localStorage is now a cache and sync outbox, not the source of truth.** Everything still persists under one key, `babyname-swipe-v3` (`STORAGE_KEY` in `src/BabyNameSwipe.tsx` — **never change this string**, it would orphan every cached swipe). Access still goes through `window.storage.get/set(key, sync)` (`src/lib/storage.ts`), a holdover from the original prototype's storage API.
- Shape of the cached object:
  ```
  {
    account: { lastName, genderFilter, onboarded },
    swipers: [
      { slot: 0, label, position, block: [{ position, name, gender }], exhausted },
      { slot: 1, label, position, block: [...], exhausted },
    ],
    picks: { [name]: { [slot]: { verdict: "keep" | "no", decidedAt, gender? } } },
    outbox: [{ slot, name, verdict, decidedAt }],
    syncedAt: string | null,
  }
  ```
  `picks` is nested by slot rather than a single verdict per name, since two swipers can independently decide the same name and both verdicts have to be representable at once — `data-model.md`'s client-cache sketch doesn't spell this out but the six-table schema (`picks` PK is `(account_id, slot, name_id)`) requires it. `block` is a swiper's dealt-but-not-yet-decided run — cards are removed from it the moment they're swiped or undo puts them back, so `block.length` alone drives the low-water-mark refill (FR-021) and the "Finding more names…" vs. exhausted UI split.
- **Every swipe is written to the outbox synchronously**, before any network call (FR-019). The outbox flushes to `POST /v1/picks` on reconnect, before the next deck-block request, and on sign-out (`src/lib/syncQueue.ts`) — never on every individual swipe, so offline swiping never blocks on the network. A flush deletes only server-acknowledged entries; `accepted` from the response is "how many entries off the head of the outbox the server took," not a count of changed rows — treating it any other way resends picks forever.
- **Matches and keeps are derived from `picks`, not from a pool.** They used to be `pool.filter(...)` against a client-side name list, which meant any name missing from the pool silently vanished from Matches — real data loss when the pool changed (spec 001). That principle carries forward: a pick whose gender isn't known locally (e.g. hydrated from `GET /v1/state`, which doesn't carry gender) is always shown; a pick with a known gender is scoped to the active girl/boy/both view.
- **Sign-in is required** (FR-001) — there is no guest mode. On sign-in, `GET /v1/state` hydrates the cache from the server, replacing it entirely (this is intentionally a full overwrite, not a merge — the server is authoritative for account/swiper/pick state). That hydration is gated so it only runs once per sign-in, not on every Supabase token refresh, and the UI shows a loading state until it completes — showing the pre-hydration local fallback (which defaults to `onboarded: false`) even briefly would flash the Welcome screen at an already-onboarded returning user.
- **Migration**: a cached object with no `account` key but a `people` array (the pre-backend shape) is a one-time migration case — it's converted into the new shape and its picks are queued into the outbox so they sync once signed in, rather than discarded.
- "Reset everything" now clears both the account server-side (`POST /v1/reset`, scope `everything`) and the local cache — the confirmation copy says so, since it's no longer device-scoped.

## Name pools

- **The corpus lives server-side now** (`api/src/babynames_api/corpus/names.json`, seeded into the `names` table via `make seed-corpus`) — spec 002 moved it off the client, and `src/lib/nameCorpus.ts` is gone. The frontend never holds the corpus; it only ever sees the handful of cards in its current `block`, fetched via `POST /v1/deck/next`.
- Generated by `scripts/build-name-corpus.mjs` from the SSA's public baby-name archive (1880–2025) — the same script also still emits a TypeScript module (unused by the frontend now, but not removed from the generator) for parity checking. Regenerate with `npm run corpus:build`, check invariants with `npm run corpus:verify`.
- 63,880 real names total: `GIRL_CORPUS`-equivalent 39,749, `BOY_CORPUS`-equivalent 24,131. The corpus is **generic on purpose** — narrowing the deck is the job of the AI criteria filter (spec 003), not of a curated pool. Don't reintroduce build-time name rules.
- **Two knobs, don't confuse them**: `--min-uses` (default 25 all-time births) sets what's *in* the corpus. The **core** (`--core-min`, default 300 births since `--core-since` 2005) sets what gets dealt *first*. Deck quality is an ordering problem, not a size problem.
- Each list is **core-first**: girl core 7,457, boy core 5,707. Core entries are ranked by births since 2005, the tail by births since 1995 — an index/rank is a popularity rank in both parts, which spec 003 consumes for "common but not top-10" criteria, and which `names.rank`/`names.is_core` now store directly (`data-model.md`).
- The deck deals the **core in a popularity-weighted random order** (`deal_block` in `api/src/babynames_api/deck.py`, a faithful Python port of the original `weightedShuffle`: each name draws `key = u^(rank+1)`), then the tail flat-shuffled. Tuned so the median of the first 20 cards sits near rank 180 with roughly one card in six from deeper. **The float64 underflow that makes this fall back to strict rank order past ~card 2,118 is reproduced deliberately, not fixed** — see `docs/remaining-items.md` §2.
- **Per-account, not global, seeding**: FR-014 retired the single global seed `20260730` — each account gets its own `deck_seed` at creation (`accounts.deck_seed`), so two accounts with the same gender filter see visibly different orders, while both swipers on one account (and that account on any device) see the identical order, since they share one `served_order`.
- Girl and boy lists share **zero spellings** (a name is assigned to whichever gender used it more all-time) — enforced at the database level by `names.name` being globally unique, not per-gender, since picks are keyed by name and a collision would let a pick in one gender silently affect the other.
- The corpus's removal from the bundle saved ~217 KB gzip (the exact number `scripts/validate-corpus-ui.mjs` was written to check pre-cutover; that script assumes the old client-only, no-auth architecture and needs updating — or a Playwright-driven replacement using a minted test JWT — before it can validate anything post-cutover).

## Screens / flow

1. **Loading** — brief centered text while `useStore()` reads localStorage, the Supabase session check resolves, and (on a fresh sign-in) `GET /v1/state` hydration completes.
2. **Sign in** (only when there's no session) — full-page, email + magic link via Supabase Auth. Replaces all chrome, same as Welcome.
3. **Welcome** (only when `!state.account.onboarded`, and only after hydration — see Data model & storage above) — full-page, replaces all chrome. Collects your name (required), partner's name (optional), last name (optional), and a girl/boy/both selector, then persists locally and via `PUT /v1/settings`, and drops straight into the swipe screen. No separate "confirm" step.
4. **Swipe** (default view) — the main screen. Layout top to bottom:
   - Header row: a **segmented control** (one pill, two tappable halves, a sliding dark "thumb" behind whichever swiper is active) on the left for choosing who's swiping; "MATCHES · N" chip and a flat outlined gear icon on the right, vertically aligned to the bottom of the segmented control.
   - Card stack (flex, fills remaining vertical space) — a "Hello My Name Is" sticker: colored band up top (pink for girl names, blue for boy names, chosen per-card via `item.g`; a neutral slate tone instead whenever the swiper's `genderFilter` is "both", regardless of the individual card's gender) with "HELLO / MY NAME IS", then a ruled cream writing area showing the name in cursive, with the last name (if set) smaller and muted gray directly beneath it. No shadow, no per-depth lift/scale animation, no card-number counter — these were all removed deliberately (see "Design decisions" below). Swiping drags/rotates only the top card; cards behind it are visually identical and don't move when the stack advances.
   - Controls row: ✕ (pass) / ↺ (undo, disabled when no history) / ♥ (keep) — plain circular buttons, unchanged since the original prototype.
5. **Matches** (toggled via the "MATCHES · N" chip) — full list of names both swipers kept ("Both said yes"), then the current swiper's own keeps, then Copy Backup / Restore (JSON via clipboard or a prompt fallback) and a destructive "START [NAME] OVER" button that clears just that swiper's picks (and the corresponding slot on the server, via `POST /v1/reset`).
6. **Settings** (toggled via the gear icon) — **fully replaces the screen**, no header/chrome carried over, since it's a distinct context, not swipe-adjacent. Same four fields as Welcome, pre-filled, **auto-saving** on a ~400ms debounce as you type/toggle (no explicit Save — this was a deliberate simplification over an earlier Cancel/Save version). Below the fields: a "RESET EVERYTHING ON THIS DEVICE" danger button (confirm dialog → wipes the account server-side and the local cache, dropping back to Welcome), a "SIGN OUT" button (flushes the outbox once, then clears the cached account/picks/block — FR-006), then an "About" section (portfolio link, GitHub source link, "Build [short commit sha]"), then a single "BACK" button pinned to the bottom.

## Other standing features

- **Update-available toast**: `useUpdateCheck()` polls `/version.json` (written by CI with the deploying commit's SHA) against `import.meta.env.VITE_COMMIT_SHA` baked into the running bundle, on an interval and on tab refocus. On mismatch it shows a small pill near the top: "New version available — install now?" with an INSTALL button that just does `location.reload()`. There's no service worker in this app (unlike `contraction-timer`) — this polling is the only update mechanism, and a user must force-quit/reopen or tap Install to actually get new code, since the page can sit open indefinitely otherwise.
- **Mobile viewport hardening**: `100dvh` (not `100vh`) + `overflow: hidden` + `overscroll-behavior: none` on both the app root and `html`/`body`, plus `env(safe-area-inset-*)` padding throughout — this stack was built up over several rounds of fixing real iOS Safari bugs (rubber-band scroll, notch/home-indicator overlap, horizontal pan from a WebKit flexbox `min-width: auto` bug). Any new full-bleed layout work should keep `minWidth: 0` on flex children to avoid reintroducing that horizontal-scroll bug.
- **iOS input zoom**: all text inputs are pinned to `fontSize: 16` — WebKit auto-zooms the page on focus for any input under 16px and doesn't reliably zoom back out. Don't drop this below 16.
- **No card shadow, on purpose**: box-shadow was tried multiple ways (depth-based, then flattened, then split across separate transform/shadow/overflow-clip layers to dodge known WebKit compositing bugs) and real iOS Safari kept rendering it inconsistently in ways neither Chromium nor even a real WebKit build on Linux (see below) reproduced. It was removed entirely rather than keep chasing engine-specific rendering. If shadow ever comes back, test it on an actual iOS device before trusting any local render.
- **WebKit testing locally**: Playwright's WebKit browser can run on this Linux box for cross-engine checks the default Chromium-based testing misses (`npm install playwright`, `npx playwright install webkit`, `sudo npx playwright install-deps webkit` for the GTK/GStreamer system libs it needs). It's WebKitGTK, not Apple's actual engine, so treat a clean render there as strong evidence, not proof, for iOS-only bugs.

## Design decisions worth preserving

- Everything is intentionally low-key/muted (dusty pink/blue, terracotta accents) — a bright/saturated palette was explicitly rejected twice (red card band called "sickly," a slate/gray option called "millennial gray").
- Motion is minimized on purpose ("people are gonna fire through these quickly") — no lift/scale animation on the card stack, no shadow-driven "pop" when a card advances, no per-card counter to distract from the swipe itself.
- The segmented control (not two separate toggle buttons) was a specific, considered choice to visually merge "who's swiping" into one component, freeing up header space for Matches/Settings.
- Settings is deliberately a separate full-screen context (not layered over swipe chrome) with auto-save instead of Cancel/Save, on the reasoning that a settings screen shouldn't need an explicit commit step for simple profile edits.
